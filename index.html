01Internal agent platformIn progress · GA targeted Q1 2027Runtime / Release / Memory

Agent Platform

Teams own what an agent does.
The platform owns how it runs.

The mandate was a single sentence: teams need to build and ship an agent in four hours. Meanwhile, every product team building an agent was re-solving the same undifferentiated problems: voice transport, observability, sessions, and release. The Agent Platform separates agent configuration from agent execution so those problems get solved once.

Product teams own prompts, tools, and configuration. The platform owns execution, versioning, eval-gated release, and deployment. Release control is chosen per agent and per environment: a sales demo agent can ship with a button click, while agents that handle payments and personal data ship through a git-managed, engineering-owned path.

My role

Co-owner of the platform end to end: one of its two technical owners, accountable for the whole system and its production behavior. Primary author of the real-time voice plane, runtime deployment strategies, and shared memory and session management.

Ownership contract

  • Product teams ownPrompts · tools · configuration
  • Platform ownsRuntime · versioning · eval gates · release
  • Release pathsButton-click · git-managed CI/CD
  • I co-ownThe whole platform, end to end
  • I primarily authorVoice plane · deployment strategies · memory & sessions
  • In buildAgent identity · cost governance · long-term memory · Temporal integration · MCP gateway

A deployment is a versioned release of agent configuration, evaluated before it reaches production.

Status

The voice gateway runs inside the platform today. The platform is the target foundation for agents across the organization, with product teams onboarding ahead of GA.

Inside the work

The design tension

Business stakeholders wanted one-click deployments. Engineering teams wanted CI/CD-grade testing before anything shipped. Per-agent release modes resolved it without forcing one answer on every agent.

Why it exists

Vendor surfaces we might have built on were deprecated, and every team’s implementation hit the same failures. A platform that owns execution also keeps vendor choices reversible.

Netflix relevance

This is the role’s shape: a core primitive owned end to end, offered as a paved path, with the day-2 operations and release gates a non-deterministic system needs.

02Developer experienceDesign proven · pre-productionSDK / CLI / Git

Meet engineers
in their own codebase.

The platform launched UI-first, which worked for executive demos and business users. Engineering teams pushed back hard, and some refused to adopt it without a CLI and a git workflow.

I designed and proved the path for engineers to build with platform primitives from their own repositories: agent definitions as versioned code, synced to the platform, released through the same eval gates as everything else. A sensitive agent keeps git as its source of truth; a demo agent can stay in the UI.

I extended the same idea to the runtime: a path for agents to execute on Google’s enterprise agent platform instead of our internal runtime service, while keeping the platform’s contracts, versioning, and release gates.

My contribution

Interaction-plane design, the proof of concept, the deployment strategies behind both release paths, and the Google runtime path.

Two planes, portable runtime

  • Business usersUI configuration · button-click release
  • EngineersCode in their repo · CLI sync · CI/CD release
  • SharedPrimitives · versioning · eval gates
  • Runtime targetsInternal runtime service · Google enterprise agent platform

Management mode is chosen per agent and per environment, because agent sensitivity varies widely.

Why it matters

It turned the platform’s loudest internal critics into a design input, and it’s the adoption path for engineering-owned agents.

03Real-time agent systemsVoice / Streaming / Latency

A voice agent is
a systems problem.

I built the foundation of the agent harness behind Lumina Workforce, part of RealPage’s publicly launched Lumina AI Suite: orchestration, voice transport, and agent runtime. It now handles about 7,000 live calls a day. Nobody asked for the audio gateway: I identified the pattern and pushed to build it because it stabilizes voice latency and quality. It now runs inside the Agent Platform.

The hardest problem was latency. It turned out to be performance engineering across the whole real-time path, including blocking work hiding inside async Python. One voice activity detection (VAD) change, run as a controlled A/B test, cut latency by 689 ms (p < 0.001, Cohen’s d = 1.04). Guardrails were another major driver of voice issues in our resident agent, so I implemented and tuned them to fit inside the latency budget.

My contribution

Harness and gateway architecture, speech integrations, the real-time audio path, and latency diagnosis across the call lifecycle.

04Evaluation infrastructureEvals / Quality signals / Replay

Evals for output
with no ground truth.

Fixing latency raised a bigger question: why couldn’t we see when voice quality was getting worse? Voice output has no ground truth and nothing practical to label, and nobody in the organization had a concept of audio-based evals yet.

I proposed and designed a reference-free, three-layer audio eval suite, then took it from a locally runnable CLI prototype into the organization’s eval stack. The suite can replay recorded audio, and eval sets deliberately target difficult-caller scenarios.

I also helped architect the pipeline our evals team runs, which turns structured OpenTelemetry traces from failed production runs into single- and multi-turn regression evals.

Public reference implementation: github.com/lackmannicholas/voice-evals

My contribution

Audio evals: concept, design spec, prototype, stakeholder buy-in, and integration with the evals team. Trace-to-eval pipeline: initial architecture.

Three evaluation layers

  • Layer 1Acoustic & perceptual quality (MOS predictors)
  • Layer 2Conversational dynamics
  • Layer 3Audio LLM-as-judge

Reference-free and unsupervised: zero per-clip labeling, which removed the labeling overhead that had blocked the idea.

Result

Before the audio suite, voice quality drifted [N] times over [window] before anyone caught it. There has been no significant drift since. Next step: parsing production recordings directly into single-turn audio eval cases.

05Shared agent libraryPython / LangGraph

Agentix

One orchestration foundation.
Six agents across fifteen channels.

I built Agentix by extracting core agent logic out of an application service into a reusable Python package, then integrating it back into the product. It runs LangGraph workflows for Leasing SMS, chat, email, nurturing, and voice, and became the foundation other agent teams built on.

I built session and shared-state management into Agentix, and again on the OpenAI Agents SDK when the organization standardized on it and I led the migration off the framework I had built.

My contribution

Design, core extraction, package implementation, product integration, and the later SDK migration.
